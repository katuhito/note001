# ThinkPad T480sのUSB-C充電不良に、SPIフラッシュの外部書き込みで挑んだ記録 ―― 直らなかったけれど、得たものは大きかった

※この記事にはアフィリエイトリンク(広告)が含まれています。

## はじめに

手元のLenovo ThinkPad T480sが、USB-Cでうまく充電できなくなりました。

調べていくと、この世代のThinkPadには「Thunderboltのファームウェアが壊れて、USB-Cの充電がおかしくなる」という有名な不具合があることが分かりました。そして、すでに壊れてしまった場合は、ソフトウェアの更新では直せず、基板上のチップに外部から直接ファームウェアを書き込むしかない、ということも。

整備の現場では、症状から仕組みを逆算して原因を詰めていくのが基本です。今回もその考え方で、基板上の8ピンのチップと向き合ってみました。

先に結論を書いておくと、**充電は直りませんでした**。それでも、この過程で分かったこと、つまずいたことは、同じ症状に悩む人や、これからPC修理に踏み込む人の役に立つと思うので、記録として残します。

## 症状

- 純正の45W USB-C充電器で、「ワット数の高い充電器を使用してください」という警告が出る
- 電源を切った状態なら100%まで充電できる
- 充電器をつないだまま作業すると、バッテリー残量が少しずつ減っていく
- 65WのUSB PD充電器(Anker Nano II)に替えても、同じ警告が出る

充電器を替えても変わらないので、充電器ではなく本体側の問題です。

## 原因の見立て：Thunderboltファームウェアのバグ

T480sは、Lenovoが公式に告知している「Thunderboltのソフトウェアとファームウェアの重大な更新」の対象機種です。

告知されている症状には、

- USB-Cアダプターをつないでもバッテリーが充電されない
- Thunderboltコントローラーがデバイスマネージャーに見えない
- USB-CからのHDMI出力ができない

といったものが並んでいて、今回の症状とぴったり重なります。

仕組みはこうです。Thunderboltコントローラーは、自分のファームウェアを基板上の小さなフラッシュメモリー(W25Q80、1MB)に入れています。初期のファームウェアにはバグがあり、充電器を抜き差しするなどのたびに、このチップへログを書き込み続けます。やがてチップが満杯になると、Thunderboltと**急速充電が止まり、低速の充電だけが残る**。

「電源を切れば満充電できるが、使用中は足りない」という症状は、まさにこの説明どおりでした。

すでに満杯になったチップは、Lenovoの更新ツールでは直せません。ここで、外部のプログラマー(書き込み装置)で、チップに直接正しいファームウェアを書き込む、という手段が出てきます。手順は、オープンソースのBIOSプロジェクトLibrebootの資料を参考にしました。

## 用意した道具

- CH341Aプログラマー(USB接続の書き込み装置)
- SOIC8クリップ(基板上のチップを、半田付けせずに挟む道具)
- 作業用のPC(Ubuntu)と、書き込みソフトのflashrom
- テスター
- Lenovoの公式サイトからダウンロードした、T480s用Thunderboltファームウェア

ファームウェアは、Lenovoの`.exe`を`innoextract`で展開して`TBT.bin`(256KB)を取り出し、チップ容量の1MBに合わせて後ろをゼロで埋めて使います。

## つまずき1：何度やってもチップが返事をしない

クリップをチップに噛ませて認識させようとしても、flashromは「No EEPROM/flash device found」。詳細表示では、チップからの返事が`0xff`(全部1)のままでした。

チップからの返事は2番ピン(DO)を通って戻ってきます。何も返ってこないと、プログラマー側では全部1に読める。つまり「チップが返事をしていない」状態です。

テスターで電圧を当たっていくと、電源の8番ピンは3.3V出ているのに、**7番ピン(HOLD)が0V**でした。HOLDはチップの「一時停止」ピンで、ここが0Vだとチップは命令をすべて無視します。

原因は拍子抜けするほど単純でした。CH341Aのソケットには、**24シリーズ用と25シリーズ用の2つの区画**があり、変換基板を**24シリーズ側に挿していた**のです。24シリーズの区画では7番ピンがGNDにつながっているので、HOLDが落ちたままになっていました。

25シリーズ側に挿し直した途端、`W25Q80.V`をあっさり認識。整備でいえば、カプラーの差し込み位置が1つずれていた、という類の話です。

## つまずき2：5Vの信号

認識したので書き込みに進もうとしたところで、クリップの1番ピン(CS)の電圧を測ると、**5V近く**ありました。

安く出回っている黒い基板の旧版CH341Aは、電源は3.3Vでも、信号線に5Vが出る個体があります。チップの許容範囲を超えるうえ、その信号線は基板上でThunderboltコントローラーにもつながっています。ここで一度手を止め、3.3Vに切り替えられるCH341A V1.7を取り寄せました。

## つまずき3：3.3Vのプログラマーでは書き切れない

V1.7は電圧も設定も正常なのに、認識が不安定で、書き込みは毎回同じ場所で失敗します。

次に、Librebootが推している**Raspberry Pi Pico**をプログラマーにしてみました。Picoにserprogというファームウェアを入れると、USB経由でSPIの読み書きができる道具になります。ブレッドボードで配線して試すと、消去はきれいに通りました。

ところが書き込みは、何度繰り返しても**0x4000以降で、約23万バイトが毎回失敗**。速度を下げても、数も場所もほぼ同じです。

一時はチップの劣化を疑いましたが、後で分かったのは、Picoの**読み出し自体が化けていた**ということ。2回読んだ結果どうしが一致しないのです。照合のための読み出しが化けていたので、書き込みの成否も正しく判断できていませんでした。

基板に付いたままのチップは、信号線がほかの回路(Thunderboltコントローラー)ともつながっています。3.3Vの弱い信号では、その負荷に負けて、読み書きがうまく通らなかったと考えています。

## 一発で通った、その理由

最後に、計測をし直したうえで、旧版のCH341Aに戻して試しました。すると、消去・書き込み・照合2回が、**一発で成功**。それまで15回繰り返しても終わらなかった作業が、あっけなく終わりました。

違和感を覚えて、改めて旧版の1番ピンを測り直すと、やはり5Vでした。最初の計測は正しかったのです。

5Vの強い信号だから、基板上の負荷を押し切って書けた。速く、一度で終わったのはそのためです。ただしこれは、部品を傷めるリスクと引き換えの結果で、人に勧められるやり方ではありません。

ちなみに、この過程でもう一つ失敗をしています。ファイルを1MBに埋める`dd`コマンドを、ファイルが無い場所で実行してしまい、**中身がゼロだけの1MBのファイル**を作っていました。気づかずに一度それを書き込み、「すでに同じ内容です」という表示で異変に気づいた、という一幕もありました。

## 結果：充電は直らなかった

ファームウェアを書き込んだ後、BIOSにはThunderboltの設定項目が戻り、コントローラーは認識されるようになりました。Thunderboltのドライバー、ファームウェア更新ツール、BIOSも最新にしました。

それでも、

- 充電器の警告は消えない
- USB-CからのHDMI出力もできない
- Windowsのデバイスマネージャーに、Thunderboltコントローラーが出てこない

という状態は変わりませんでした。

ファームウェアでできることはやり切ったので、原因はUSB-Cまわりの回路(電源を交渉するPDコントローラーや、Thunderboltコントローラーそのもの)のハードウェアにあると判断しました。メーカー修理は本体の価値を超えそうなので、中古のT480sを手に入れて使い、この個体は修理の練習台にすることにしました。

## この方法で直る例もある

今回は直りませんでしたが、外部からThunderboltのファームウェアを書き直す方法そのものは、**実際に直った例が多く報告されている、実績のある対処法**です。私の個体は、ファームウェア以外の部分にも不具合を抱えていた、と考えるのが自然だと思います。

- **Librebootの手順書(T480 / T480s)**：チップが満杯になってThunderboltと急速充電が止まった場合でも、外部から正しいファームウェアを書き込めば、起動後にUSB-CとThunderboltが正常に動くようになる、と説明されています
  https://libreboot.org/docs/install/t480.html
- **Heads(osresearch.net)のT480s向け手順**：この「充電の不具合」に悩む場合は、外部書き込みで直せるとして、修正済みのファームウェアを用意しています
  https://osresearch.net/T480s-maximized-flashing/
- **coreboot公式ドキュメント(T480 / T480s)**：この不具合で動かなくなった場合の唯一の解決策は、別チップに入っている修正済みのThunderboltファームウェアを外部から書き込むこと、とされています
  https://doc.coreboot.org/mainboard/lenovo/t480.html
- **Lenovo公式の告知**：対象機種と症状の一覧、予防のための更新方法が掲載されています。まだ壊れていないなら、まずはこちらの更新が最優先です
  https://support.lenovo.com/hn/nb/solutions/ht508988
- **ThinkPads Forum**：T480とT480sを手に入れてすぐにThunderboltのファームウェアを更新したところ、その後も充電の問題は起きていない、という予防の体験談があります
  https://forum.thinkpads.com/viewtopic.php?p=879403

同じ症状でも、原因がファームウェアだけなら、この記事の手順で直る可能性は十分にあります。試すなら、**3.3Vの信号のプログラマーを使うこと**、そして**基板上で書けなければ、早めにチップを外してソケットで書くこと**をおすすめします。

## 振り返り：次に同じことをするなら

- **基板に付いたまま3.3Vで書けないときは、早めにチップを外す。** ソケットに入れて基板の外で書けば、ほかの回路の影響を受けません。今回いちばん時間を使ったのは、在基板の書き込みにこだわったことでした
- **照合の失敗が「毎回同じ場所・同じ数」なら、読み出しの化けも疑う。** 2回読んで一致するかを確かめるだけで、切り分けが進みます
- **計測値の訂正を受けたら、自分でもう一度測る。** 5Vの再確認を怠ったことが、結果的にリスクを取る判断につながりました
- **書き込む前に、ファイルの中身を必ず見る。** `hexdump`で先頭を見るだけで、ゼロだけのファイルは防げます
- **Lenovoの展開フォルダには、`TBT.bin`と`ASSISTTBT.bin`の2つがある。** 通常は`TBT.bin`を使います
- **Thunderboltのファームウェアは、壊れる前に更新する。** これに尽きます。中古のThinkPadを手に入れたら、真っ先にやるべきことです

## おわりに

直らなかった修理の記録を書くのは、少し気が引けます。それでも、今回の作業で、

- SPIフラッシュの外部書き込みの手順
- プログラマーごとの電圧や駆動力の違い
- 基板に付いたままの書き込みの難しさ
- 症状から仕組みを逆算して、テスターで一つずつ原因を詰めていく流れ

を、自分の手で確かめることができました。

直った、直らなかったという結果だけでなく、直そうとしていく過程にこそ、仕組みを理解するための情報が詰まっていると思っています。この記録が、同じ症状のThinkPadを前にした誰かの、判断の材料になればうれしいです。
